控制件与 L1 基座依赖风险

图生图 / ControlNet 有没有对应件 · 「L1 过度信赖基座」这条警告的核查结果

2026-10-03设计稿（未实现）触发：用户警告含一处地基级缺口
两个结论

① 参考图理解「有，而且比 IP-Adapter 强」（CharaBridge 内建，还多解一层几何）；空间密集控制「有对应件，但属"能做但贵"」（条件包 / 编辑包，需独立分支 + 天级重训）——而用户「只为了生成角色才要它」的判断成立，因为常规生态里 ControlNet 的两个职责，在 KP 里已经被拆走了。

② ⚠️「L1 过度依赖基座」成立，而且更准确的说法是「从未检验」——设计的选层判据里根本没有 L1，而 L1 承担约 90% 的需求。

所以不是一个"有 / 没有"的问题，是"在哪一层"的问题：

  • 参考图理解 → KP 是内建且升级的。IP-Adapter 只提取外观特征然后并联注入；CharaBridge 额外解出几何。对二次元尤其占便宜——平面着色下几何条件信噪比高，几乎不受材质干扰。
  • 空间密集控制 → 有对应件但不在主干内，这是有意的：主干的条件输入位只有「文本 + latent + 身份 token」，depth/pose 这类新模态要挂一个带 encoder 的分支，被设计成可插拔的外挂，不是主干的一部分。

1.2 ⚠️ 一个必须先说清的隐患：40ch 混合 latent 会让 img2img 生态全部重写

下游 img2img / inpaint / 放大节点全部假设固定通道数

我们的是 40ch 混合 latent → 现有生态工具全部不通用。这不是"能不能做"，是"做出来也没人能用"——这条路线早期没有任何生态杠杆可用。

1.3 但你的直觉是对的：常规生态里 ControlNet 干的两件事，在 KP 里已经被拆走了

常规工作流里 ControlNet 表面上在做"控结构"，实际同时承担了两个完全不同的职责：

常规里 ControlNet 实际在承担的职责KP 里由谁承担
① 锁结构 / 锁姿态（保持构图，不让它跑掉）语义 8ch 通道（原生管结构）——§4.2 明确写「语义通道承担这是什么、在哪、什么姿态」
+ Layout token（K=16 个可学习布局 token，4×4 粗网格 + 2D 位置编码）
+ 弱监督直接复用 3D 合成数据的 bbox / depth（零额外标注成本）
② 参考图定角色（我要的是"这个角色"）角色卡 / CharaBridge——给正反两图 → 前向 → 秒级出卡
于是得到一个很干净的判断

· 只要你「这个角色」→ 不需要 ControlNet。走角色卡（秒级，不打架，跨版本可迁移）。

· 要「像素级锁死这个姿势、只换画风」→ 还是需要条件包。而它是「能做但贵」（独立分支 + 天级重训），且早期没有生态可用（§1.2）。

1.4 结论：这条不进第一步

三条理由，每条都是独立的：

  1. 不是刚需（用户自己的判断，且设计支持）；
  2. 成本档是"天级"（§4.8 成本档：新模态 = 独立分支 + 重训）；
  3. 有前置依赖：它要挂在能力总线的外挂加载框架上（P1.5），那套框架现在还不存在。

→ 建议：写进 P3 之后的可选清单，不占当前预算。现在记下来只是为了"不忘记它存在、以及为什么不做"。

02⚠️ 你的警告：L1 过度依赖基座

2.1 最硬的证据：设计的「选层判据」里，L1 完全缺席

主文档 §4.8 的选层判据原文是：

第一问：底模见过这个分布吗？
   没见过 → 支撑集外扩 → L2 ∥-Pack
   见过   → 第二问
第二问：它被人为抑制过吗？
   是 → 恢复型 → 闭式算子 E⁻¹ / Δ-Pack（秒–小时）
   否 → 长尾型 → Δ-Pack（小时）
注意：两问只在 L2 与 L3 之间分流。L1 完全没有出现在判据里。

而 L1 承担的是 约 90% 的需求（L2 ≈ 9%、L3 ≈ 1%）。

也就是说：占比 90% 的控制路径，从来没有经过任何判据的检查。它被预设成"免费已得的能力"。

你的说法还可以再加重一层

这不只是"过度信赖"，而是「从未检验」。信赖至少隐含"我看过它表现"；而这里连看都没看过——判据根本没为它设过入口。

2.2 四条风险机制

风险 1 · 覆盖率假设 —— "90%" 是调用量分布，不是已验证能力

L1 之所以能号称覆盖 90%，隐含要求：主干的风格条件轴覆盖足够广。这是一个隐藏假设。而设计文档已经识别了一个同类假设——§4.8.5 的「通道分离退化」，并称它为"全案第二个隐藏关键假设"（第一个是 NVFP4 QAD）。

但漏掉了这一个 —— 它其实是第三个，而且更外层

通道分离退化会让 L1 失真；覆盖率不足会让 L1 直接不存在。

风险 2 · 隐式接口不可独立验证，且不可修

L3（Δ-Pack）L1（主干条件轴）
本质写入（直接改权重 / 子空间系数）请求（希望基座理解这个轴）
可审计性可做谱检查 §4.9 条目 17 硬约束：发现正交入侵维度即判定包不合格无法独立检查 只能靠出图间接看
出错后能否修能 重训这个包（小时级），或直接不用它修不了 轴在基座内部，只能重训主干
控制权归属我们基座

→ 这一列对比就是"过度依赖基座"的精确含义：控制权从我们手上转移到了基座手上，而且转移得无声无息。

风险 3 · ⚠️ 与 E5 实测直接咬合 —— 低比特下 L1 可能被"抹平"

这是本文件唯一有实测数据支撑的风险，而且它把两轮工作连起来了。E5 已实测（真实 Sana 1.6B，15 例平均）：

配置noise_pred 相对误差峰值位置
W4A167.74%—
W4A8（设计档）9.98%—
W4A429.72%t≈500 时冲到 35.4%（倒 U 形）

而且端到端出图证实：W4A4 的误差表现为轨迹漂移（固定种子下给出"另一个同样合理的样本"，构图变了但画质正常）。

把两件事放在一起看

L1 用的恰恰是一个低维、连续的控制信号。而量化噪声最可能摧毁的，正是这种信号。

两个具体机制：

  • (a) 噪声被误读为控制信号：控制向量和采样噪声住在同一个隐空间里。当量化把噪声预测打偏 30%，主干接收到的"应该往哪走"的信号里，混进了与风格轴同量级、但方向随机的成分。
  • (b) 分辨率压缩（更隐蔽，也更致命）：FP4 的激活只有 16 个量化级（E2M1）。如果风格信息是通过激活的精细结构传递的（这是 L1 的"连续可调"所要求的），那么只有 16 级的量化会系统性地压缩这个轴的分辨率。
    → 外在表现不是"画错了"，而是：旋钮行程变短、转到一半就饱和、中间一大段值给出同样的输出。功能还在，但"连续可调"这个 L1 的核心卖点消失了。

这个风险是可实测的，而且现有验证门 G0–G7 全部没有覆盖它。

风险 4 · 条件轴互相耦合

§4.8.5 处理的解耦是通道间的（语义 8ch ↔ 细节 32ch）。但 L1 还要求轴与轴之间正交：转"厚涂"旋钮不应连带改变构图密度、光照方向、色彩饱和。

而这里有一个天然的验证手段被漏掉了

§4.8.4 的 shader 配对数据：同一 3D 场景、不同 shader，几何/光照/相机/姿态完全一致，只有渲染风格不同 → 条件向量的差异理论上只应落在风格维度上，其余维度必须是零。这是一个免费的正交性监督信号，此前只被当作"数据来源"。

2.3 加固方案（五条：不推翻 L1，但给它上保险）

① 措辞纠正：90 / 9 / 1 是调用量分布，不是能力分层

L1 覆盖 90% 的调用量，但 L3 承担 100% 的兜底责任

L1 是默认档（快路），L3 是一等公民（保底）——两者的地位不按使用频率排。现在的表述（"覆盖约 90%" / "底模确实没见过的东西 → 约 1%"）会诱导一种危险读法："L1 够用了，L3 很少要用"。

② 新增 Axis Probe（条件轴探针）+ 验证门 G3.5

这是把 L1 从"信仰"变成"可验证"的核心动作。四测：

测项判据不达标后果
单调性轴值单调递增 → 输出沿该维度单调变化轴不成立 → 该风格改用 L3
正交性转该轴时，构图（bbox 布局差）、光照（亮度/色温）、色相漂移 < 阈值轴耦合 → 拆分或改用 L3
可逆性+a 再 −a 回到原图（容差内）不可逆 → 不可用
⚠️ 低比特可用行程FP4 下可分辨的轴步数 ÷ bf16 下的步数 > 阈值（如 ≥ 70%）L1 退化 → 必须改用 Style-Pack（方案 ③）

③ Style-Pack：把风格也做成"显式对象"（最优雅的一条）

设计里已经有这个机制了——Character Carrier（补充 04 §3.3）：参考图 → Fitter 前向 → 得到一个数据对象（1–5MB）。

给 N 张同风格参考图  →  Style Fitter 前向一次  →  Style-Pack（数据对象）
收益说明
不依赖基座理解风格不再要求"基座见过这个轴"——它被显式编码在对象里（绕过风险 1）
可检查对象是数据，可比对、可求相似度、可看它变了多少（绕过风险 2）
可迁移 / 可分享与角色卡同理：不依赖坐标系，跨我们自己的主干版本可迁移
零新增架构复用 Fitter + 载体格式，没有新机制
格式统一补充 04 条目 22 已提出「TypographyPack 与角色卡共用分层表示」→ 加 Style 是自然的第三项。三类载体共用一套格式，load_adapter() 一个入口
这就是这条警告的正面解法

不是把 L1 做强，而是给"风格"也备一条显式路径，让 L1 只需承担它真正验证过的部分。

④ 设计律（新增）：控制权原则

能显式写入的，就不要隐式请求。

L1 是「我们向基座请求」（可被拒绝、可被误解、无法审计）；L3 / Pack / 载体是「我们直接写入」（可检查、可回滚、可迁移）。

在 ① 低比特（FP4）+ ② 自研架构（我们控制主干）+ ③ 摆脱基座束缚（项目初衷） 这三条同时成立的项目里——写入优先于请求。

→ L1 只用于「轴独立性经探针验证过、且低比特行程达标」的那些维度。未经 G3.5 验证的维度，默认归属 L3。

与补充 03 §2.2 那条设计律互为对偶

补充 03 说"能力越大、越域外，就越不能住在 ΔW 里"（大能力不能塞小容器）；本条说"关键的控制权不能交给不受控的对方"（可靠控制不能依赖隐式请求）。两条合起来，构成控制手段的完整分工边界。

⑤（附带）L1 的显式化改造：让它真的可以被信赖

这是唯一能让 L1 本身变可信的办法（而非绕过它）。

不要让 L1 是一个裸数值，而是给它一个已命名、逐维标定的低维条件向量（例如 16 维，每一维对应一个已命名的风格轴：写实度 / 描边强度 / 平涂度 / 冷暖 / 对比度 / 笔触粗度…）。

训练时用 shader 配对数据强制逐维独立 —— 因为 shader 本身是正交的（同一场景不同 shader，几何 / 光照 / 相机 / 姿态完全一致），所以条件向量的差异理论上只应落在 shader 维度上，其余维度必须是零。

这样 L1 就从「黑盒旋钮」变成「已标定控制面板」

用户看到的不是一个 0–1 的神秘数字，而是"描边强度 0.3、平涂度 0.7"这种可预期、可复现、可文档化的东西。

而且它已经躺在设计里（§4.8.4 的 shader 配对），只是没有被赋予"正交监督"这个用途。

05一句话总结

① 参考图理解有（CharaBridge，且比 IP-Adapter 强）；空间密集控制有对应件（条件包），但它是"能做但贵"、且进不了第一步——而"只为了角色才需要它"这个判断在设计上成立。

② 「L1 过度依赖基座」这条警告成立，而且更准确的说法是「从未检验」：设计的选层判据里根本没有 L1 的入口，而它承担 90% 的需求。

加固的方式不是把 L1 做强，而是 ① 把 90/9/1 读回"调用量分布"、② 加 G3.5 探针把 L1 从信仰变成可验证、③ 给风格也备一条显式路径（Style-Pack）、④ 立一条设计律：能显式写入的，就不要隐式请求。
