能力总线与文字渲染

可插拔能力接口 —— 「小模型 + 专家模型」到底怎么成立 · 文字渲染与版式规划

2026-10-02配套主文档 v1.1本轮产出 v1.2 修订

00三件事其实是同一件事

你这轮问了三件事，串起来看是一条线：

  1. 能不能留一个可插拔的接口，以后挂新东西不用重训？
  2. 「专家模型」和「小模型」怎么连——听起来矛盾，到底什么意思？
  3. 能不能让它自己写文字、自己排文本框？
三者共享同一个结构：冻结的小主干 + 一组按需挂载的能力包

第 3 件事看起来是另一件事，其实它是第一个被设计的能力包——而且它恰好能测出这个接口的极限在哪。所以这份文档的主线是：先讲接口，再用「文字」当第一个真实案例把它撑满。

01「小模型」和「专家模型」怎么连

它们不是二选一，是叠起来的两层

这是你卡住的地方，一句话就能解开：

小模型是底座，专家是挂件。不是两个模型去挑一个，是同一次推理里两个东西同时在干活。

最贴切的比喻是手机和 App：

手机（小模型 / 主干）App（专家 / 能力包）
什么时候在每次开机都在你点开才加载
占多少资源全部（0.6–1.5B）一点（约 13M 参数一个包）
怎么变强换手机（重训，巨贵）装 App（训一个小包，很便宜）
谁改谁不动挂在它身上

「不用重新训练」指的就是：手机不出厂，装个 App 就行。

但要先澄清：「专家模型」这个词有两个意思

你的困惑有一半来自这个歧义。

说法正式名是什么你需要吗
LoRA 专家 / 能力包Mixture of LoRA Experts、Adapter Bank挂在冻结主干上的低秩小模块，输入相关的门控决定开哪个这就是你要的
稀疏专家 / MoEMixture-of-Experts（Switch Transformer 那一类）主干内部把 FFN 拆成 N 个专家，每个 token 只走 1–2 个不是这个
为什么 MoE 不适合你（这点反直觉，必须说清楚）

MoE 省的是算力（FLOPs），不是显存。全部专家的权重都得驻留显存，只是每次只激活一部分去算。

对 8GB 卡来说，MoE 是负担更重的那一类。而且它必须随预训练一起设计，天然违背「以后挂上去」的诉求。

所以你听到的那个「不用重新训练、像专家模型一样的做法」，指的是第一行：LoRA 专家池 + 路由器。这在 LLM 上已经成熟，2025 年也大量搬到扩散模型上（T2I 生态里的 LoRA 专家、风格/主体自适应融合都是热点）。

① 关键判据：什么能装成包，什么必须进预训练

这是整份文档最值钱的一段。「可插拔」不是万能的，能力有一条明确的分界线：

低秩扰动 ΔW = AB 只能做 rank-r 子空间内的改动

· 目标输出和底模已有输出在同一支撑集内（只是概率质量重新分配）→ ΔW 有解，能装包。

· 目标输出在支撑集之外（底模几乎不可能产生这种东西）→ ΔW 无解，必须进预训练。

低秩适配能改「怎么画」，不能改「看得见什么」。
能力类型能否做包原因
画风（厚涂 / 赛璐璐 / 水彩 / 特定画师风）分布重分配完美适配底模会画这些，只是概率不均
角色 / 主体身份分布重分配完美适配只锁一个方向，正交约束下代价低
领域倾向（建筑 / 商品 / 医学插画 / 机甲）分布重分配能做，rank 要大底模已有这些概念，欠采样而已
构图 / 镜头语言偏好分布重分配能做同上
文字渲染支撑集外扩做不成纯 LoRA字在主干 latent 里根本不存在（见 §03），不是容量问题，是信息不存在
手部解剖精度支撑集外扩勉强，性价比低需要主干表征本身变细
空间关系推理支撑集外扩同上这是表征层的能力，不是风格层
新条件模态（depth / normal / pose）新输入通道需新增分支主干没有对应输入位，要加 encoder

这张表直接决定了架构该怎么切：画风 / 角色走包，文字走分支，空间推理走主干设计（这正是补充 01 里 Sigmoid 注意力 + layout token 要解决的）。

02能力总线（Capability Bus）

四个作用维度

普通 LoRA 生态的问题是「所有包都往同一块地盘挤」——这就是跟底模打架的物理原因。解法是先把地盘分成四个正交的轴，每个包只被允许在指定的轴上动手：

维度控制什么机制典型用途
Layer-scope作用在哪些层每层独立门控向量风格偏浅层、结构偏深层
Channel-scope作用在哪个通道组语义通道(8ch) / 细节通道(32ch)风格只写细节，身份只读语义
Time-scope作用在哪些 timestep时间相关门控早期定构图、后期定质感
Space-scope作用在哪些像素区域ROI 掩码文字、局部贴图、分区控制

Channel-scope 那一行继承主文档 CharaBridge 的设计，现在把它从角色专用升级为全局机制——这是「不打架」最省力的结构性前提：两股力量在物理上不抢同一块张量，就天然不会互相污染。

Pack 的物理形态与体积

一个能力包 = {低秩权重 ΔW, 门控向量 g, 元数据}。按 1.5B 档主干（24 层、d_model=1536、MLP 4×）实算：

覆盖范围参数量BF16 体积
仅 attention（q/k/v/o）约 4.7M约 9 MB
全层（attention + MLP），rank=16约 13.6M约 27 MB
全层，rank=32约 27M约 55 MB
全层，rank=64（领域包级）约 54M约 110 MB
这就是「笔记本里的 100 个 App」

100 个 rank-32 包 = 5.5GB 磁盘，但显存上只需按需挂 3–4 个（约 200MB）。

这是「更大的未来选择」在工程上真正成立的原因 —— 选择变多，显存不变。

门控与 bit-exact 保证

每个包的门控标量初始化为 0，且门控的加法在量化器之后进行。

全部门控 = 0 时，模型输出与原底模逐位一致（bit-exact）。

这不是修辞，是可测的验收项。它的意义是：接口本身零风险——你挂 100 个能力包的代码，但只要不打开，画的图和裸模型一模一样。

所有实验都建立在这个不变量上。

冲突仲裁：从「调权重」升级到「正交化」

补充 01 里我提过「冲突的本质是两股力量抢同一块地盘，降学习率只是被动缓解」。现在给出主动解法的谱系：

方法机制代价
降权重 / 降 lr被动削弱冲突治标，且削弱效果
LoRA Dropout + 早停抑制过拟合同上
门控归一化softmax 分配，总量守恒仍有耦合
正交化投影（NP-LoRA 式）用 SVD 找出 A 包的主方向，把 B 包的更新投影到其零空间再加推理时有投影开销，但最有效
时间分段（TSM 式）不同 timestep 用不同包，非对称混合需为时间维额外训练
一条硬证据：LoRA 专家「朴素平均 / 均衡共享」会掉点

2025 年多项消融得到一致结论。所以不要用简单的 Σ αₖ·ΔWₖ，必须走门控或正交化。

必须绕开量化器（这条是坑）

社区已证实：FLUX 的 4-bit 路径上 LoRA 会静默失效

diffusers #9291 / #10989，直到 v0.32.2 才修 —— 不出错、不报错、风格完全没变。

机理很直白：如果注入点在量化之后、且量化器又把增量吃掉，那 ΔW 的扰动等于没发生。

架构层强制规定

能力包的注入点必须位于 NVFP4 反量化之后、BF16 域内；且入包前对注入点做回归测试（改权重 → 输出必须变化）。

03文字渲染

SDXL 为什么根本不会写字

不是没训好，是四个原因叠起来：

  1. 文本侧：CLIP 的目标是整句图文匹配，字符级结构不进入表征——它知道「这张图里有招牌」，但不知道招牌上是什么字。
  2. 数据侧：图文对的 caption 里极少写「图中有字 XXX」，甚至把文字当地物噪声标注。
  3. 监督侧：没有字符级信号，模型只学到「这里有文字的质感」，不学「具体是什么字」。
  4. 空间侧：8× latent + 512/1024 分辨率下，一个汉字在 latent 里只有几格，字形笔画分不开。

结果就是你熟悉的那个现象：画出「看起来像字但不是字」的伪文字。

社区里有一句总结得极准：

“Diffusion models are great at suggesting text and terrible at writing it.”
模型很擅长暗示这里有字，极不擅长写出字。

诚实说明

推论：文字能力的天花板不是参数量

是 ① 字形条件 ② 数据配方 ③ 课程学习。

这对我们是天大的好消息——我们不需要 20B，我们需要正确的配方。

① 一个绕不过去的物理约束：32× 压缩把字吃掉了

现在讲我们架构的特殊麻烦，而且它是个硬约束。主文档为了低显存选了 32× 压缩：1024² 的图 → 主干只看到 32×32 = 1024 个 token。

那么一个汉字有多大？

项数值
1024² 图像下的主干 latent 网格32 × 32
一个高 40px 的汉字占几个格1.25 格
印刷可读下限 24px 的汉字占几个格0.75 格

看下面这张图 —— 同一个 40px 的汉字，在两种压缩率下的下场完全不同：

同一块图像区域，同一个 40px 汉字。网格 = 主干看到的 latent 格子。
一个汉字还不到一个格子大。字在编码阶段就被丢了。

这不是训练问题，是信息问题：任何 rank 的 ΔW，都无法从一个「不包含这个字」的表征里造出这个字。这也是 §01 那句判据的物理来源。

那降回 8× 压缩行不行？——不行，显存会炸：

latent 压缩率1024² 的 token 数后果
8×（SDXL / Flux 量级）16384注意力 O(N²)，8GB 直接爆
16×4096勉强，显存翻 4 倍
32×（我们的主干）1024低显存目标的根基
结论：主干一动不能动，文字必须走另一条路

这个 trade-off 是整份设计里必须显式承认的——「文字好」和「显存小」在同一个 latent 里是互斥的。

三条路线

T0 · 零训练风险，行业已在用
确定性排版
模型只负责画，文字全部由字体引擎渲染后合成。Layout Planner 出框和内容 → FreeType/Pillow 光栅化真字体 → 合到成图上。

优点：正确率 100%，绝不出错字；任意字体/描边/竖排；中文零成本。
缺点：字是「贴上去」的，不参与光影融合（无透视、无材质、无遮挡）。
适用：同人志嵌字、条漫、信息图、海报。
T1 · 推荐，我们做这个
字形条件分支
在冻结主干旁边挂一条低压缩 ROI 分支：裁 ROI → 4× 压缩编码 → 字形灰度图 + 位置图 + 字体 embedding 拼接 → AttnX 式 cross-attn 注入 → 字符级 CTC 监督。

参数量：encoder 约 50–150M + AttnX 约 200–400M，总计 < 0.6B。
可行性已证实：同类方案（AnyText2）官方 demo 8GB 显存就能跑。
优点：字与画面真正融合（透视、材质、光照一致）。
缺点：字错了就是错了，需 OCR 奖励筛选兜底。
T2 · 贵，暂不做
端到端预训练
把文字数据直接混进预训练 + 课程学习（先无字后有字、先短句后长段，Qwen-Image 的配方）。

需要：低压缩 VAE 或高分辨率 + 海量文字图文对 + 大规模算力。
代表：Qwen-Image 20B、LongCat-Image 6B、Seedream 4.0。

结论：等 T1 跑通、且算力到位了再升级。T1 的 ROI 分支设计不会作废——它可以直接变成预训练阶段的结构先验。

两条注入机制的取舍（AnyText2 论文的总结，直接引用）：

  • 「prompt 里的条件 embedding」→ 泛化不到未见过的字符
  • 「latent 里的辅助像素」→ 预渲染字形与 caption 融合不充分
  • → 正解是两者组合，用 WriteNet 把文字生成从图像生成里解耦出来，再融合

① 我的选择：T0 + T1 双轨，且做成一个包

场景走哪条
漫画 / 条漫嵌字、对正确率零容忍T0（确定性排版）
招牌、衣服、书本上的字（要与画面融合）T1（字形分支）
两者都要T1 出图 → T0 校正 → 可选 OCR 校验
关键设计决定：把文字做成 TypographyPack —— 一个「自带分支的能力包」

它比普通 LoRA 包重（多了 encoder + AttnX + ROI 分支），但它仍然是可插拔的：

· 不装它 → 就是干净的画笔，零污染，bit-exact
· 装上它 → 多一项写字能力，主干权重不动
· 想升级文字能力 → 只换这个包，不用重训主干

这样你那句「想给它套更多东西、又不想重训」在文字这个最难的例子上就成立了。

顺手得到一条经验法则：

能装的包只改权重（LoRA）；必须加的包可以带结构（分支）

——只要主干保持冻结、门控可关断。

04版式规划器：让它「自己会文本框」

「跟同人志嵌字一样，自己会文本框、自己会写字」——这其实是两个任务，一定要拆开：

子任务本质归谁
决定字放哪、放多大、怎么断行、气泡朝谁符号推理 + 几何输出独立的 Layout Planner（小模型）
把字画到画面上（融合光影材质）像素生成TypographyPack 的 ROI 分支
不要指望 DiT 做版式规划

这是典型的任务错配——DiT 是像素分布模型，让它输出几何约束等于用锤子拧螺丝。给它一个专门的规划器，成本极低且可控。

输出 schema（可直接用）

{
  "canvas": { "w": 2480, "h": 3508, "reading": "rtl", "gutter": 24 },
  "panels": [ { "poly": [[0,0],[1200,0],[1200,1600],[0,1600]] } ],
  "items": [
    { "type": "bubble", "poly": [[...]],
      "tail_to": [820, 940],
      "text": "你还活着啊。",
      "font": "SourceHanSans-Bold", "size": 26, "align": "center",
      "emphasis": [ { "range": [2,4], "style": "bold" } ] },
    { "type": "sfx", "poly": [[...]],

规划器只输出这个结构，一个字像素都不碰。渲染由下游确定性地做。

第二条腿：合成 —— 这条是「白拿」

字体光栅化是确定性的、成本约等于 0：用字体引擎无限造页面 → VLM 反标 → 得到近乎无限的 (布局, 文字) 对。

这是整个设计里唯一一种「零成本无限扩增」的训练数据。中文 6763 常用字 × 数千字体 × 无限背景组合。

你第一轮说「数据源暂时不考虑，但如果有更聪明的供给方式也行」——这就是那个更聪明的方式：让数据由渲染器免费生成，而不是去爬别人的图。

一条值得抄的训练经验（来自漫画生成研究）

MangaDiffusion（21,142 页数据集，FID 143.5 vs SD3.5-Large 197.8）用了两个招：

  1. inter-panel attention：同一空间位置的 token 跨面板通信 → 学全局版式和阅读顺序，但不串内容
  2. 局部掩码策略：训练时把对话框区域从 attention 和 loss 里 mask 掉，逼模型专注画画

第 2 条直接印证了 §03 的核心判断：「文字」和「画面」必须解耦训练。模型画出乱码，往往是因为被逼着在气泡里同时学画画和学写字。

关于你说的「不限全年龄」那类内容

架构上它就是上面表格里的一行，和「画风包」在结构上完全同类（低秩适配器 + 门控），不需要为它做任何特殊设计——能力总线天然就覆盖了这类扩展。

具体那一类内容我不参与生成，也不参与它的训练数据制作。技术上唯一值得记的是：它比画风包更依赖 空间定位条件和结构先验，而这正好复用了上面的 space-scope 与条件包机制——所以「留接口」这件事本身不需要你现在做任何额外动作。

中文单字覆盖文字能力≥ 70%（对标 LongCat-Image 90.7 / Qwen-Image 58.3）
长文本（>20 字）可读率长文本≥ 90%
Layout Planner 框位 IoU版式≥ 0.7
面板数控制漫画结构输出面板数 = 脚本数，误差 0

07风险

风险严重度说明
「伪正交」中高低秩扰动之间实际仍有耦合，门控 / 投影只能缓解不能根除
文字分支与主干抢地盘中与「LoRA 打架」同机理，需通道隔离 + α/β 可调
量化器吃掉注入中已被社区证实（diffusers #9291/#10989），必须在架构层强制旁路
T1 训练数据规模中字形可白拿，但真实场景文字（透视、材质、遮挡）仍需采集
Manga109 许可低但必须查商业使用需单独确认
Layout Planner 分布外低真实排版风格千变万化，小模型可能过拟合主流风格

08路线修订

在原有 P0–P4 上插入两个动作：

阶段动作目的依赖
P0NVFP4 QAD 掉不掉点验证（不变，必须最先做）保住量化基础—
P1能力总线骨架：门控 + bit-exact 回归测试先把不变量立起来P0
P2T0 确定性排版链路（Layout Planner + 字体渲染）用最低成本先拿到「会写字」独立，可与 P0 并行
P3TypographyPack（ROI 分支 + 字形条件）文字与画面融合P1
P4正交化仲裁（NP-LoRA 式投影）多包共存不打架P1
顺序上有个便宜可捡

P2 完全独立于量化主线，可以现在就开跑。

它不需要 NVFP4、不需要主干、甚至不需要训练——先下载字体 + 造合成数据，就能拿到一个「会排文本框」的规划器原型。这是全案性价比最高的一块。
