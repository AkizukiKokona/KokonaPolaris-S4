| # | 发现 | 为什么重要 |
|---|---|---|

## 1. 你的两条判断，被文献证实到什么程度

你说 LoRA：**泛用性极差** + **功能性极其有限**。这两条我上一轮已经确认过。本轮**第一条找到了更深的机理**，而且它比「换底模 = 换坐标系」更致命。

### 1.1 「打架」的真身：入侵维度（Intruder Dimensions）

MIT CSAIL 的 *LoRA vs Full Fine-tuning: An Illusion of Equivalence*（arXiv 2410.21228）做了谱分析：

- **全量微调**：训练后的权重矩阵，其奇异向量**仍然高度对齐**于预训练权重——它只是**在原有子空间内调整幅度**。
- **LoRA**：产生了全新的、**排名很高的奇异向量，近似正交于预训练权重的所有奇异向量**。作者称之为 **intruder dimensions（入侵维度）**。
- **后果**：带入侵维度的 LoRA 模型「**成为预训练分布的更差模型**」，且**连续学习能力更差**。两者在目标任务上分数可能一样，但出了这个分布就散架。
- **解法**：**高秩 + rank-stabilized（rsLoRA）** 的 LoRA 能显著靠拢全量微调。

> **这就是「打架」的物理图像**：不是"学得不够好"，而是**它在底模的空间里凿了一个新维度**。凿得越深，底模原有的结构就被挤得越厉害。它**不是覆盖，是侵入**。

### 1.2 「功能性有限」的定量版本

*LoRA Learns Less and Forgets Less*（arXiv 2405.09673，Columbia + Databricks）：

- 全量微调学到的更新，其**有效秩是常见 LoRA 配置的 10–100 倍**；
- 在**continued pretraining**（持续预训练，也就是"学新领域"）场景下，LoRA 即使 r=256 也补不平差距；
- 但在**指令微调**场景下，r=256 可以基本补平——**任务越结构化，低秩越够用**；
- 而且 LoRA **忘得少**——这是个真实收益，别丢掉。

ICLR 2026 的 *Gradient Intrinsic Dimensionality Alignment* 进一步量化：

- 全量微调的梯度**本征维度（GID）通常在 30–1000**，而常用 LoRA 的 r 是 8–16 → **差距可达 100 倍**；
- **敏感性 ≠ 复杂度**：某层可能很重要但很简单，也可能不重要但很复杂；
- **Transformer 里 `W_o`（输出投影）的 GID 始终最高**——它是"注意力多头信息的合成器"；
- 解法 **RaLoRA**：用**块对角分解**把 LoRA 拆成 `diag(B₁A₁, …, Bₙl Aₙl)`，**把有效秩从 r 提到 n_l × r，而参数量完全不变**。r=8 的参数预算可以拿到 128–512 的有效秩。实测超过 DoRA、AdaLoRA，GLUE 平均 +5%。

> **这三篇合起来给你一个结论**：LoRA 的问题**不是"低秩"，是"低的有效秩"**。而有效秩**可以不改参数量就拉上去**。

## 2. 结论：不要再问"LoRA 还能怎么改"，要问"什么该给谁做"

### 2.1 三件套（图 1）

| | **身份载体** | **并联包 ∥-Pack** | **叠加包 Δ-Pack** |
|---|---|---|---|
| 形态 | 数据对象（文件） | 旁路网络 / 条件编码器 | 权重扰动 ΔW |
| 改什么 | 给主干**注入条件** | 给主干**加一条并联通路** | **改主干权重本身** |
| 典型规模 | 1–5 MB | 100M–1B 参数 | 27 MB（全层） |
| 会不会打架 | **物理上不可能** | **物理上不可能** | **会**，必须约束 |
| 能不能跨主干版本 | **能**（数据不依赖坐标系） | **能**（旁路只依赖接口约定） | 需子空间约束才勉强能 |
| 该做什么 | 角色身份、3D 姿态、结构控制 | 跨域能力（写实）、文字渲染、版式 | 同域长尾倾向（笔触、色调、细节偏好） |

### 2.2 分工边界是数学规定的，不是产品选择

这是本轮最重要的一条设计律，**直接从 §1.1 推出来**：

> **ΔW 是可以"入侵"底模的；旁路和条件不能。**
>
> 所以：**能力越大、越"域外"，就越不能住在 ΔW 里。**

推论：

- 身份 → **载体**（它是"这个角色长什么样"的完整描述，信息量远超任何低秩扰动，但它完全不碰权重）
- 跨域能力（写实、文字） → **并联包**（体量大、性质是"加一条新通路"，天然不覆盖旧通路）
- 同域长尾（笔触、色调） → **叠加包**（小、且必须锁在底模已有的 SVD 子空间里）

**回答你"LoRA 是不是最优解"这个问题**：是，但**只在第三列**是最优。它的参数效率、零推理延迟、生态成熟度都无可替代——**没有理由换掉它，只需要限制它的作用域**。你猜的"互补而不是竞争"，是对的，而且分工边界是死的。

## 3. 你那个「另一种炼丹方式」：身份载体（Character Carrier）

你的原话我复述一遍，确认理解：**给角色的完全正面图 + 完全背面图，用类似炼丹的方式"训练"它，就能换出这个角色；理论上这两张图的信息量接近一个 3D 模型。**

### 3.1 先说一个反直觉的判断：「完全正 + 完全反」对二次元反而是**强**约束

从纯几何重建角度，正/反两视图是**最难的配置**——180° 间隔，**没有任何重叠区域**，传统多视图立体（MVS）至少要 3 张且有重叠。

但**对二次元角色，情况反过来了**，理由有三条：

1. **轴对称是行业规范**。二次元角色设定图天然正面左右对称，背面也一样。「完全正 + 完全反」正好落在设计的对称面上，把左右两侧的一半信息**免费补全**。
2. **二次元的几何靠轮廓线承载，不靠光影**。写实照片的"正+反两张"里，大量信息在漫反射/阴影/材质里，而这些在二次元里**根本不存在**——信息几乎全在**轮廓线 + 轮廓内色块边界**上，两者的并集已经覆盖了绝大部分形状。
3. **写实的正/反两张图几乎不可能是同一个人同一姿势**（现实里拍不到），而二次元的正/反**是同一张设定图的两个视图**，所以它们**严格一致**——这消除了最大的误差源。

> **所以你的直觉是对的**：这两张图对二次元角色的约束，**确实比它看起来强得多**。

### 3.2 但**不要反解 3D 网格**——反解「角色卡」

这是本轮最实用的一条。See-through（SIGGRAPH 2026，arXiv 2602.03749）的论文明说：

> "a full 3D modelling pipeline often **impractical and aesthetically incompatible** for anime artwork"

它的做法是：

- 把一张插画拆成 **19 类语义 RGBA 层**（头发、脸、衣服、配件…），**每一层都把被遮挡的部分补全（inpaint）**；
- 再推一个 **pixel-level pseudo-depth / 绘制序**，解决二次元特有的一类难题：**头发丝与脸交错穿插**，不是简单的自下而上叠层；
- 数据引擎**从商用 Live2D 模型反推标注**——因为 Live2D 内部的 ArtMesh 本身就带确定性的绘制序和可见性掩码，等于**免费的像素级 ground truth**。产出了 **9,102 个完整标注的 2.5D 模型**。

**为什么这对我们是关键**：二次元角色的"3D 信息"在行业里**本来就以 2.5D 分层形式存在**（VTuber、2D 游戏、视觉小说的标准形态）。硬要做网格，你会**丢掉画风**——因为二次元的美学就住在"分层 + 平面着色"里。这跟我们前面定的「语义通道管结构、细节通道管画风」是**同一条思路**。

### 3.3 三段式：一次训练 → 秒级换人 → 可选精修

| 阶段 | 做什么 | 频率 | 成本 | 是否碰主干 |
|---|---|---|---|---|
| **① 一次训练** | 训一个 **Character Fitter**：输入 1–2 张视图，输出**角色卡**（19 层 RGBA latent + 伪深度 + 身份 token） | **一辈子一次** | 一次性，数据白拿（见 §3.5） | 不碰 |
| **② 每个角色** | 用户给正/反两张图 → Fitter **前向一次** → 得到角色卡 | 每次换角色 | **秒级**，峰值显存约 1.2GB | 不碰 |
| **③ 可选精修** | 在角色卡的**小参数空间**里跑几步拟合，或（想要极致时）再叠一个**子空间约束 Δ-Pack** | 想要更好才做 | 分钟级 | 第③种才碰，且被约束 |

> **这就是你要的"另一种炼丹"**：形式上还是"我给它素材，它学会这个角色"，但**梯度不再落到底模权重上，而是落到一个几 MB 的数据对象上**。于是三件事同时成立：**不打架**（主干没动）、**跨版本可迁移**（数据不依赖坐标系）、**秒级**（不需要几百步优化）。

**信息量对比（估算，需实测）**：角色卡 ≈ **1–5 MB**，全层 rank-16 LoRA ≈ **27 MB**。而角色卡描述的是「这个角色本身」，LoRA 描述的是「相对底模的偏移量」。**载体更小，但语义更完整**——因为它不依赖底模。

### 3.4 更激进的版本：把"炼丹"变成"一次前向"

arXiv 2511.03156（Samsung AI，2025-11）走了一条更狠的路：**用 Hypernetwork 直接从参考图预测 LoRA 权重**，完全不微调。它的两个技巧值得我们抄：

- **输出正则化**：避免"模仿底模优化轨迹"的不稳定，效果等价于自动早停；
- **HM-CFG（Hybrid-Model CFG）**：采样时**混合底模的构图能力与个性化模型的身份保真度**，用一个 κ 调权衡。在 DreamBench 上不微调即超过 DreamBooth。

**对我们的形态**：不要让 hypernet 去预测"主干权重"（那还是 ΔW，还是会有入侵维度），而是让它**预测「角色卡的条件编码」**——即 hypernet 输出的是**对身份 token 的调制**。这样连 §3.3 的第②③步都省掉：**给图，出角色，零优化**。

### 3.5 数据线：现在有现成的了

上一轮我说"3D 资产线要自己搭"。本轮查到两条**已经存在的**：

| 数据源 | 规模与规格 | 用途 |
|---|---|---|
| **NOVA-Human**（NOVA-3D，arXiv 2405.12505） | **10.2k 个 3D 二次元角色模型**（来自 VroidHub 的 VRM），渲染 **16 个随机视角 + 4 个固定正交视角（front/back/left/right）**，共 **163.2k 张图**，512²，A-pose，**仅漫反射光照**，带精确相机参数 | 训 Fitter 的**完美配对**：正/反输入 ↔ 任意视角 ground truth |
| **See-through 数据引擎** | 从 **9,102 个商用 Live2D 模型**自举出 19 类语义层 + 遮挡补全 + 绘制序标注（代码已开源） | 训「2.5D 分层解算」的监督信号 |

**为什么 VRM 这条线特别值钱**：VRM 是 VTuber 生态的标准格式，**带骨骼、贴图、表情混塑**。意味着一个资产可以渲染出：**任意视角 × 任意姿势 × 任意表情 × 任意光照**。上一轮说的"用渲染器生产数据，而不是去爬别人的图"——这里可以直接兑现成**二次元角色的无限配对数据**。

> ⚠️ **许可证必须核查**：VRoid Hub 上每个模型有**独立的作者授权设置**（有的禁止商用、有的禁止再分发、有的禁止用于 AI 训练）。这套数据只能用于**研究 / 内部验证**，**绝不能直接进可分发权重**。真正要商用，必须走**自己建模或购买授权**的资产线。See-through 的数据引擎同理。
>
> 另外一个好用的技巧（业界现成做法）：**用 3D 侧视图反投影去补全 AI 立绘的正视图**——因为「AI 不会画标准三视图」是行业公认痛点，而我们的 Fitter 恰恰需要标准三视图做输入。这条可以反向用：**我们自己造标准正交视图的数据，而不是指望用户提供**。

### 3.6 序列预算：身份 token **必须走 cross-attention**，不能 in-context 拼接

⚠️ 一个容易照抄踩坑的地方。InstantCharacter 用 **`nb_token=1024`** 把身份 token **拼进主序列**——在 12B 的 FLUX 上没问题。

**但在我们这里会出事**：我们全图只有 **1024 个图像 token**。再拼 1024 个身份 token，**序列直接翻倍**，注意力成本翻 4 倍，显存第一性原理瞬间失效。

**我们的解法**：

- 身份 token 压到 **256 个**（而非 1024）；
- **不进主序列**，而是通过 **cross-attention 只挂载到少数锚点层**（我们本来就是 3:1 线性:Sigmoid，锚点层天然是 softmax 族的少数派）；
- 好处三重：**序列不膨胀**（省显存）、**与文本 token 完全隔离**（不会二次稀释文本注意力——正好呼应你最痛的"长提示涣散"）、**门控 g=0 时 bit-exact**（可关断）。

## 4. 写实 / 二次元：这个"拓展包"该怎么分层

你的原话：**"它既可以画写实，也可以画二次元，这个应该是后期也可以就跟拓展一样去更改它。"**

这里必须先切开两件不同的事：

### 4.1 「同域风格」和「跨域」不是一回事

| 你要的效果 | 性质 | 该谁做 |
|---|---|---|
| 赛璐璐 / 厚涂 / 水彩 / 某画师笔触（都是二次元） | **同域内的风格偏移** | **叠加包 Δ-Pack** 足够（27MB，秒级切换） |
| 二次元 → 写实（材质、次表面散射、真实光照模型） | **跨域，支撑集外扩** | **并联包 ∥-Pack**，或直接进主干 |

### 4.2 首选方案：让"写实"成为主干**内生**的一根轴，而不是外挂

既然我们本来就要自己训练主干，最干净的做法是：**预训练阶段就让主干同时覆盖 photo 与 anime 两个域**，用一个 **domain 条件向量**切换。做法上只是多一个 embedding 维度 + 数据配比，**不增加任何推理成本**。

**这么做的收益**：

- "写实"从「外挂能力」变成「主干固有旋钮」，**天然不打架、不占显存、可连续插值**；
- 你以日系为主的诉求依然满足——只是把 anime token 设成默认值；
- 顺带覆盖了**半写实 / 国风插画 / 3D 渲染风**这些"中间态"，它们本来是二次元主干最难外扩的方向。

### 4.3 备选方案：事后加，那就必须是「域包」= 并联包

如果主干已经训完是纯二次元，事后确实能加，但**必须是并联包，不能是 ΔW**。理由见 §2.2：

- 旁路网络（ControlNet 式）**并联**在主通路上，**物理上不可能清除**底模原有能力；
- 而 ΔW 高秩 = **直接改写底模 = 制造入侵维度 = 打架**。

**代价要说清楚**：并联包的体量比 Δ-Pack 大两个数量级（100M–1B，FP4 下约 50–500MB 显存），且**必须重训过一次**（不是"挂上去就行"）。所以它是**"能做，但贵"**——首选还是 §4.2 的主干内生方案。

### 4.4 以日系二次元为主，带来的 4 个便宜和 2 个约束

**便宜**（这些让我们的目标变简单了）：

1. **平面着色 → 几何条件（normal / depth）的信噪比更高**，几何分支几乎不会被材质干扰，CharaBridge 的几何侧更可靠；
2. **轴对称规范 → 「正 + 反」两视图约束显著变强**（§3.1）；
3. **2.5D 分层 > 真 3D**（§3.2），表征更简单、更保画风；
4. **数据线现成**：NOVA-Human（10.2k VRM）+ Live2D 引擎（9,102 模型）+ Danbooru 的 19 类语义标注体系（`wd-eva02-large-tagger`）——**标签体系可以直接对齐**。

**约束**（两个要提前规划）：

1. **"写实跨域包"要更早进规划**。纯二次元主干的写实先验**几乎为零**，比混合域主干更难外扩——所以 §4.2 的"双域预训练"如果要做，**必须在预训练阶段就决定**，事后补的成本高得多；
2. **文字渲染在二次元里权重更高**（同人志嵌字是刚需），而 See-through 的 19 类语义层**天然可以多出一层"文本框层"**——把 TypographyPack 和角色卡用**同一套分层表示**统一起来，这是一个可以白拿的架构统一。

## 5. ComfyUI：要不要支持，成本到底在哪

**短答：不要把 ComfyUI 当路线依赖。成本不在"写节点"，在"架构特征"上。**

### 5.1 真实成本拆解

ComfyUI 的现状是：**通用 loader + 每个架构一套手写节点**。看它的源码组织就知道——`ModelMergeSDXL`、`ModelMergeFlux1`、`ModelMergeQwenImage`、`ModelMergeWAN2_1`…**每个新架构都要人肉写一份**，把该架构的 block 结构硬编码进节点里（Flux 是 "19 double + 38 single"，Qwen-Image 是 "60 transformer blocks"）。

所以：

- **好接的架构**：单文件权重、标准 diffusers 接口、标准 VAE、注意力后端可替换、LoRA 键命名符合 PEFT 约定。
- **我们的架构**恰好有三块硬骨头（图 3）：**40 通道混合 latent**、**非 softmax 注意力**、**能力总线门控**。

| 项目 | 一次性成本 | 长期成本 |
|---|---|---|
| 原生节点集（loader / VAE / 采样 hook / 包加载 / attention override） | 熟手约 1–2 周 | — |
| **维护** | — | **持续**（ComfyUI 内部 API 频繁变动，节点经常失效） |
| 生态配套（量化格式、示例工作流、ControlNet / IP-Adapter 适配） | 大 | 持续 |
| 社区节点（让别人来写） | ≈ 0 | 你自己维护 API 稳定性 |

**顺带一个未验证点**：ComfyUI 的主力低比特路径是 **fp8（`weight_dtype: fp8_e4m3fn`）和 GGUF**。**我们 NVFP4 单文件权重在 ComfyUI 上的可用性，我没有查到确证，需要并进 P0 一起实测**——因为我们整个显存优势建立在 NVFP4 上，如果 ComfyUI 接不了 NVFP4，那么在 ComfyUI 里跑我们的模型**显存优势会直接打回 fp8 水平**。

### 5.2 建议路径

**主交付**：

1. **diffusers 兼容的 `ModelMixin`** + **单文件 safetensors 权重**；
2. **一个 30 行的最小推理脚本**（比任何 UI 都重要——它是所有第三方适配的起点）；
3. 一个 Gradio / CLI 前端（够自己用、够做对比实验）。

**预留四个接口**（零成本，现在写进规范就行）：

| # | 接口 | 为什么值得现在做 |
|---|---|---|
| ① | 权重命名与 diffusers 同构、单文件 | 第三方只差一个 `load_state_dict` |
| ② | latent 的**打包 / 解包两个纯函数** | 混合 40ch latent 的最大障碍是"别人不知道怎么拆"，给两个函数就解决 |
| ③ | **attention 可替换**（不要硬编码 kernel） | ComfyUI / xformers / 第三方都靠 `set_attn_processor` 注入 |
| ④ | 统一的 **`load_adapter()`**（包 + 角色卡走同一个入口） | 避免"每个挂件一套加载逻辑"的碎片化 |

**最关键的一条**：**等模型跑出效果，让 Comfy-Org 官方化。** 证据是他们的实际行为——FLUX.2 / HiDream / Lumina "**custom nodes within days of release**"；ERNIE-Image 开源当天，Comfy-Org 就 repackage 并发布了官方工作流模板。**他们的动力来自"模型够好"，不是你写节点。** 在这之前投入两周写节点，收益远低于把主干训好。

**唯一例外**：**P2′ 的 T0 确定性排版链路**用现成模型跑，**ComfyUI 直接就能用**——这条路完全独立于我们的主干，所以 ComfyUI 在这个子任务上是零成本白拿的。

## 7. 路线更新

```
P0   验证 NVFP4 QAD 掉不掉点          ← 最高优先级，几天可验证
     └ 并入：NVFP4 单文件在 ComfyUI 的可用性（未验证）
P1   换 Latent（32× 混合）
P1.5 能力总线骨架（含四接口 + 双向包体系）
P2′  T0 确定性排版链路                ← 独立，可立刻开跑，ComfyUI 直接可用
P2.6 角色卡数据线 + Character Fitter  ← 本轮新增，独立可并行，纯数据 / 不依赖主干
P2   换主干（含 双域预训练 + domain 条件向量）
P3   CharaBridge（多视角身份 + 几何分支）
P3.5 TypographyPack（与角色卡共用分层表示）
P4   少步蒸馏
```

**新增的 P2.6 值得单独说**：它**不依赖 NVFP4、不依赖新主干、不依赖量化结论**——只需要 Fitter + 现成数据（NOVA-Human / Live2D 引擎）+ 一个 2.5D 分层表示。**它是全案第二个可以立刻开跑的部分**，而且它的产出（角色卡格式）是后面所有身份相关设计的地基。**先定格式，后接主干。**

## 8. 风险与未验证清单

| 项目 | 级别 | 说明与缓解 |
|---|---|---|
| **两视图 → 角色卡的歧义性** | 中 | 正/反无重叠区域，中间视角靠"渲染辅助监督"补（沿用对偶视角损失 + 距离引导注意力融合）。**凹结构、背面细节**仍是弱项，需实测二次元的实际误差 |
| **NOVA-Human / VRoid / Live2D 许可证** | **高** | 每个模型独立授权，多数禁止 AI 训练 / 商用。**只能研究用，绝不能进可分发权重**。商用资产线必须自建或购买 |
| **Block-diagonal LoRA 在扩散上的有效性** | 中 | RaLoRA 只在 LLM / 分类上验证过，**DiT 上是空白**。P1.5 做消融，对照 vanilla LoRA / DoRA |
| **角色卡体积估算（1–5MB）** | 低 | 基于 19 层 × 1024 token × 32ch × fp16 的粗算，**未实测**；深度图与元数据会推高 |
| **Hypernetwork 预测"条件编码"** | 中 | 现有工作只验证了"预测 LoRA 权重"，**我们的变体未被验证** |
| **ComfyUI 对 NVFP4 的支持** | 中 | **未查到确证**，并入 P0 实测 |
| **双域预训练对二次元画质的稀释** | 中 | 主干同时学 photo 可能拉低 anime 先验。需做数据配比消融；严重时退回"纯二次元主干 + 并联域包" |
| **「禁止入侵维度」的谱检查阈值** | 低 | 需要定义"正交到多少算入侵"，属于工程参数，先定 0.1 余弦相似度以内的宽松告警 |

## 附：本轮引用来源

- InstantCharacter（腾讯混元 / InstantX，arXiv 2504.12395）：单图角色定制，stacked transformer encoder 适配器，1000 万级角色数据集（paired 多视角 + unpaired 文本-图像），`nb_token=1024`，可与风格 LoRA 同时加载；官方说明 offload 推理可在 22GB 以内。列为已知局限：**动物角色相对不稳定**。
- See-through: *Single-image Layer Decomposition for Anime Characters*（SIGGRAPH 2026，arXiv 2602.03749）：19 类语义 RGBA 层 + 遮挡补全 + 伪深度绘制序；数据引擎自 9,102 个 Live2D 模型自举；明确论述全 3D 建模管线对二次元"不实用且美学不兼容"。
- *LoRA vs Full Fine-tuning: An Illusion of Equivalence*（MIT CSAIL，arXiv 2410.21228）：**intruder dimensions** 的发现；高秩 rsLoRA 可减少该效应。
- *LoRA Learns Less and Forgets Less*（arXiv 2405.09673）：全量微调更新秩为常见 LoRA 的 **10–100×**；LoRA 遗忘更少。
- *Gradient Intrinsic Dimensionality Alignment*（ICLR 2026）：GID 30–1000（差 100×）；**RaLoRA 块对角分解把有效秩提到 n_l×r，参数量不变**；**`W_o` 的 GID 最高**；敏感性 ≠ 复杂度。
- BD-LoRA（arXiv 2510.23346）：块对角 LoRA + rsLoRA（α/√r）缩放，高秩下无额外通信开销。
- *Finetuning-Free Personalization via Hypernetworks*（Samsung AI，arXiv 2511.03156）：hypernet 直接预测 LoRA 权重；输出正则化稳定训练；**HM-CFG** 平衡底模构图能力与身份保真度。
- NOVA-3D（arXiv 2405.12505）：**NOVA-Human，10.2k 个 VRM 二次元角色，16 随机视角 + 4 正交视角，共 163.2k 图，仅漫反射光照**。
- GaussianIP（arXiv 2025）：多视角注意力共享（front/back/left/right）+ **距离引导注意力融合**（中间视角按角距离混合相邻关键视角特征）——可直接借用于我们的中间视角生成。
- DirectTriGS（CVPR 2025，arXiv 2503.06900）：triplane 作为"类图像连续场"表示 3DGS，**可被 VAE 压缩后用于 latent diffusion**——"角色卡"可压缩性的先例。
- ComfyUI 源码组织（`comfy_extras/nodes_model_merging_model_specific.py`）：每架构一套手写节点；ERNIE-Image 生态资料：开源当天 Comfy-Org 即发布官方工作流模板，量化走 **GGUF / NVFP4** 两条路径。
