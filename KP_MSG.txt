fix(probe): noise_floor 单点测量撞上 0.0 -> 门关时两条噪声轴被当成真响应（63/63）

## 症状
同步云端后自检 **62/63**：
  ❌ 非空性守卫：门关时 16 条轴应全判 inert，实测 14

## 根因（实测定位，不是猜）
`RealAxisProbe.ensure_inert` 的阈值 = `16*floor + 1e-12`，
而 `noise_floor` **只测一个 batch**。噪声依赖 oneDNN GEMM 的分块形状，
分块形状依赖 batch 大小 => 某些 batch 恰好测出 0。实测（tokens=6, dim=64）：

    batch= 2 -> 0.0      batch=17 -> 2.98e-08
    batch= 5 -> 0.0      batch=18 -> 2.98e-08
    batch= 9 -> 2.98e-08 batch=33 -> 5.96e-08
    batch=10 -> 0.0  ← 巧合点！

`ensure_inert` 恰好用 `batch=sweep_steps+1=10` => floor=0 => 阈值塌成 1e-12
=> 轴 7（7.45e-09）与轴 15（2.98e-08）的**纯数值噪声**被判成「有响应」。

⚠️ 这正是该函数原注释预言的情形，只是当时用「M=612 出现、M=17 不出现」
描述成 batch 依赖，**没意识到判据自身也依赖 batch**，于是判据会自我失效。

## 修法
`noise_floor` 改为**扫多个 batch 取最大值**（最大值 = 噪声上确界，门线最保守）：
    probe_batches=(2, 9, 10, 17, 18, 33)
现在 floor=5.96e-08 => 阈值 ~9.5e-07 => 两条噪声轴正确判 inert。

## 教训
**「数值判据」不能单点采样**。若判据依赖某个实现细节（本例是 GEMM 分块），
单点测量可能恰好落在该实现的巧合点上，使判据静默失效。
凡是要拿实测值当门线，一律扫多个条件取最保守值。
