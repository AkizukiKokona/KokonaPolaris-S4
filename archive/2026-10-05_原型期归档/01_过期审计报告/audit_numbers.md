# 🔴 矛盾（8 条）

## 🔴-1 KP-M 层数：`config.py` 32 层 vs 设计文档 28 层 —— 这一条污染了「参数超标 25%」的整个结论

**位置**
- `kp/config.py:64` → `DIT_M = DiTCfg(dim=1792, layers=32, heads=16)`
- `design/KokonaPolaris_架构设计方案.md:346`（§4.3 参数量表）→ KP-M 1792 / **28** / **14**
- `design/KokonaPolaris_架构设计方案.md:1259`（附录 A）→ KP-M: `hidden: 1792, layers: 28, heads: 14`
- `.workbuddy/memory/MEMORY.md:93` → 「KP-M 主干实测 1.875B，比标称 1.5B 大 **+25.0%**」
- `kp/arch_report.py:112-116` → 「待拍板：剩下的标称差是改结构还是改标称」

**声称值 vs 实算值**

我用 meta device 真实搭建主干（`identity_anchor_layers=[1, L//2]`，与 `arch_report.py:31` 同口径）实测：

| 配置 | 层数 | 头数 | 实测总参数 | 17·d²·L |
|---|---|---|---|---|
| KP-S（config） | 24 | 16 | **0.5948B** | 541.5M |
| KP-M（**config**） | **32** | 16 | **1.8748B** | 1746.9M |
| KP-M（**文档**） | **28** | 14 | **1.6564B** | 1528.6M |

**为什么是问题**

设计文档 §4.3 表把 KP-M 标成 **1.5B**，而按文档自己的层数 28 层实算是 **1.6564B**，只超标 **+10.4%**，且「四舍五入到 1.5B 档」是合理的。
现在 `config.py` 用 32 层，参数才涨到 1.875B（+25.0%）。也就是说：

> **MEMORY.md 里那条「+25.0%，待用户拍板：改结构还是改标称」的悬案，成因有相当大一块只是 `config.py` 单方面把层数从 28 改成了 32，而设计文档从来没同意过这个改动。**

这是把一个「文档-代码同步漏改」当成了「架构决策悬案」，可能误导用户去做一次不必要的结构瘦身（MEMORY.md:99-100 甚至已给出 `dim≈1664/L32` 的候选方案 —— 而真正的问题只是 L 该不该是 28）。

**建议修法**
1. 先确认哪个是权威值。若文档 28 层为准 → 改 `config.py:64` 为 `layers=28, heads=14`，参数量落到 1.656B（+10.4%），「+25% 悬案」自动消失。
2. 若确实要 32 层（`config.py` 是新的、文档陈旧）→ 必须在 §4.3 表、附录 A、dit.py docstring、MEMORY.md 四处同步把 28→32，并把「标称 1.5B」的口径改成「1.88B 档」或说明 1.5B 指的是 KP-M **前身**。
3. 无论哪条路，`config.py` 的 `DiTCfg` 字段应加注释指向设计文档行号（现在注释只说 `KP-S（主力 0.6B）/ KP-M（质量档 1.5B）`，而这两个标称在文档里对应的是 28 层）。

## 🔴-2 KP-S / KP-M 头数：`config.py` 16 vs 文档 12 / 14

**位置**
- `kp/config.py:63-64` → `heads: int = 16`（两个档位都是 16）
- `design/…架构设计方案.md:345-346`（§4.3）→ KP-S heads **12**、KP-M heads **14**
- `design/…架构设计方案.md:1236,1259`（附录 A）→ KP-S `heads: 12`、KP-M `heads: 14`

**声称值 vs 实算值**

| 档位 | 文档 heads | 文档 head_dim | config heads | config head_dim |
|---|---|---|---|---|
| KP-S d=1152 | 12 | **96** | 16 | **72** |
| KP-M d=1792 | 14 | **128** | 16 | **112** |

**为什么是问题**

参数量**不受**影响（heads 只影响 `head_gate` 的 O(heads) 项，可忽略 —— 实测 KP-S 换 12/16 头参数量都是 0.5948B），但两个实际行为变了：

1. **QK-Norm 的归一化维度变了**。`dit.py:125-126` 的 `RMSNorm(self.head_dim)` —— head_dim 从 96 掉到 72（KP-S）或 128→112（KP-M）。RMSNorm 的统计量是沿最后一维算的，维度变了就换了归一化尺度。主文档 §4.3 L337 说「QK-Norm 必开 … 对我们的混合精度 + NVFP4 路径几乎是必需项」—— 这条现在建立在一个未对齐的 head_dim 上。
2. **head_dim=72 / 112 不是硬件友好尺寸**。72 = 8×9、112 = 16×7，都不能整除常见的 64/128 tile；而文档选的 96 / 128 是标准尺寸。补充 09 全篇的量化实测（E5 / E5b，165 个 `nn.Linear`、proj_out 敏感性、block size 敏感性）都是在 sana 1.6B（head_dim=64/128 量级）上做的，head_dim 偏离会改变 QK-Norm 与 out_proj 的实际 outlier 分布。

**建议修法**：与 🔴-1 一并定权威值后同步。若确认文档的 12/14，则 `config.py:63-64` 改 `heads=12` / `heads=14`。**特别地**，`heads=14` 对应 head_dim=128，与补充 09 实测的 128 量级一致 —— 这是一个「文档值更可能是深思熟虑的结果」的证据。

## 🔴-3 `DiTCfg.param_count()` 用 9d² 口径，与 `dit.py` 的 17d² 口径矛盾 —— 漏掉了占比最大的 adaLN

**位置**
- `kp/config.py:55-59`：
  ```python
  per_block = 4 * d * d + 2 * d * int(d * self.mlp_ratio) + 4 * d
  ```
- `kp/models/dit.py:9-16`（docstring）：「每个 block 恰好 **17·d²**」
- `kp/arch_report.py:56`（docstring）：「粗略参数量（单流主干估算，用于档案核对）」

**声称值 vs 实算值**

```
config.param_count()  per_block = 4d² + 2·d·⌊2.5d⌋ + 4d = 9d² + 4d
17d² 口径（dit.py）  per_block = attn 4d² + mlp 5d² + adaLN 8d² = 17d²
```

| 档位 | `param_count()` | meta 实测 | 比值 |
|---|---|---|---|
| KP-S | **286.86M** | 594.84M | **0.482** |
| KP-M | **925.22M** | 1874.84M | **0.494** |

我实测确认 per_block 的构成拆解（KP-S）：
```
attn qkv+out (buffer)     330.56M  ← 含 double-stream / cross-attn
mlp        (buffer)       165.75M
adaLN      (真参数)       255.03M   ← 占真参数 96.5%
```
`param_count()` 完全不含 adaLN，而 **adaLN 是单个最大的参数项（8d²，占 per-block 的 47%）**。函数低估幅度约 **-51%**。

**为什么是问题**

`param_count()` 的 docstring 说它「用于档案核对」—— 但它与真实值差 2 倍，一旦有人拿它做核对会得到完全错误的结论。实测比值 286.86/594.84 = 0.482 ≈ 9/17 = 0.529 的偏差还更大，说明它还额外漏了 double-stream / cross-attn / text_router / final_adaLN（实测见报告末表）。

**建议修法**
- 最小改动：把公式改成 `per_block = 17*d*d`，并加注释「不含 double_stream(+4d², 前 5 层) / identity_cross(+4d², 2 个锚点层) / text_router / final_adaLN —— 要精确值请用 `arch_report` 的 meta device 口径」。
- 更好：这个函数在 `kp/` 里没有任何读者（`arch_report` 用 meta device 自己算），按「零消费即删」的项目既有规范，**建议直接删除**，避免留一个错的估算器。

## 🔴-5 LoRA 训练表用「标称 1.5B」而非「实测 1.875B」算主干显存，低估 0.21GB

**声称值 vs 实算值**

NVFP4 实际位宽 ≈ 4.5 bit/param（4 bit 权重 + 每 16 元素 1 个 E4M3 scale + 每张量 1 个 FP32 scale）：

| 口径 | 参数数 | NVFP4 显存 | 文档写的 |
|---|---|---|---|
| 标称 | 1.5B | 0.844 GB | **0.84 GB** ✅ |
| 实测（config L32） | 1.8748B | **1.055 GB** | — |
| 实测（文档 L28） | 1.6564B | 0.932 GB | — |

同一条链上还有第二处口径冲突：
- §5.6 L947 明确按 **4.5bit** 算（0.6e9 × 4.5/8 = 0.3375 ≈ 0.34 GB ✅ 算术正确）
- 但 `kp/arch_report.py:90` 用的是 `rows[name] * 0.5 / 1e9` = **纯 4.0 bit**，得 KP-S **0.30 GB** / KP-M **0.94 GB**

**建议修法**

## 🔴-6 FLOPs 口径错误：把「参数量口径」当「FLOPs 口径」用了

**位置**：`.workbuddy/memory/MEMORY.md:85`；`kp/models/dit.py:32-33`

> 「⚠️ **FLOPs 两个分母别混**：adaLN **自身** −11.1%（`2·d·9d→2·d·8d`）／**全模型** −5.6%（`18d²→17d²`）」

**声称值 vs 实算值**

- 「全模型 −5.6%」：18→17 = **−5.56%** ✅ 算术本身对
- 「adaLN 自身 −11.1%」：9→8 = **−11.11%** ✅ 算术本身对

**但两个都是参数量口径，不是 FLOPs 口径。**

参数量：adaLN 是 `Linear(d → 8d)`，作用于**每层一次** ⇒ 参数量 `8d²`。
FLOPs：adaLN 的输入是条件向量 `c`（`dit.py:284` `mod = self.adaLN(c)`，`c` 形状 `[B, d]`），**不是 `[B, N, d]` 的 token 序列**。所以它的 FLOPs 是 **O(d²)，与 token 数 N 无关**；而 attention/MLP 的 FLOPs 是 **O(N·d²)**。

在目标场景 N=1024（1024² 图）：

| 项 | FLOPs（N=1024） | 占比 |
|---|---|---|
| attention + MLP（9d²·N） | 9216 d² | **99.91%** |
| adaLN（8d²） | 8 d² | 0.09% |
| **删掉一段 adaLN 的真实 FLOPs 变化** | — | **−0.001%** |

**为什么是问题**

「全模型 FLOPs −5.6%」这个说法会让读者以为 adaLN 是 FLOPs 优化项。实际上：
- 作为**参数量**结论：−5.6% ✅ 正确且有价值（adaLN 占真参数 96.5%，是体积的大头）
- 作为**FLOPs**结论：−0.001%，**等于噪声**

`dit.py:32-33` 同样问题（虽然它用了「FLOPs」一词但给的是 `18d²→17d²`，即参数量比例）。

**建议修法**：MEMORY.md L85 改成
> 「⚠️ **参数量口径下** adaLN −11.1%（`9d²→8d²`）／全模型 **参数量** −5.6%（`18d²→17d²`）。**这不是 FLOPs 结论**：adaLN 作用于条件向量（非 token 序列），其 FLOPs 是 O(d²) 而 attention/MLP 是 O(N·d²)，N=1024 时 adaLN 仅占 **0.09%** 的 FLOPs，删一段的 FLOPs 收益 ≈ **−0.001%**（噪声）。」

## 🔴-7 附录 A 的「混合注意力排布」与 3:1 比例是完全不同的两套东西

**位置**：`design/…架构设计方案.md:1264-1270`（附录 A）

**文档原文**
```
混合注意力建议排布（28 层）
L0-L8   : softmax 锚点（低分辨率 / 高噪声阶段，需要全局一致性）
L9-L27  : gated linear attention
训练时 softmax 层可稀疏化为 1/3；推理时 2K 以上只保留 L0–L4 的 softmax。
```

**声称值 vs 实算值**

| 项 | 文档 §4.3 L308 | 附录 A 排布 | 代码实测 `build_attn_plan(28,3,1)` |
|---|---|---|---|
| 总层数 | 28 | 28 | 28 |
| softmax 层 | **1**（第 0 层） | **9**（L0–L8） | **1** |
| linear 层 | 21（3/4） | 19（L9–L27） | **21** |
| sigmoid 层 | **7**（1/4） | **0** | **7** |
| 比例 | 3 linear : 1 sigmoid | 19:9 ≈ **2.1:1**，**零 sigmoid** | 21:7 = 3:1 ✅ |

代码实测（我直接调用 `kp.models.dit.build_attn_plan`）：
```
L=28 → softmax=1, linear=21, sigmoid=7
```

**为什么是问题**

1. **附录 A 这段把 sigmoid 层当成了 softmax 层**：9/28 = 32%，正好对应它自己下一行写的「softmax 层可稀疏化为 1/3」。说明作者写这段时把「每 4 层 1 个非 softmax 锚点」错记成了「前 9 层都是 softmax」。
2. **附录 A 里 sigmoid 层数 = 0**，而 3:1 比例的**全部立论**（L310–L311，含 v1.16 实测）都在 sigmoid/Softpick 上。附录 A 排布会让读者以为 sigmoid 不参与。
3. 代码实现（`dit.py:59-74`）与 §4.3 一致 ✅ —— **所以错的是附录 A，不是代码**。这条比 🔴-1 好在：代码行为有明确规范可依。

**建议修法**：附录 A L1264-1270 整段替换为
```
混合注意力排布（28 层，与 §4.3 的 3:1 一致）
L0      : softmax 锚点（唯一一次，patch embed 后初始对齐）
L1-L27  : 3 linear + 1 Sigmoid 循环 → linear 21 层 / Sigmoid 7 层
推理时 2K 分辨率：可把 Sigmoid 层的 N² scores 分块（见 §4.3 显存说明）
```
并删掉「softmax 稀疏化为 1/3」（那是把 sigmoid 记成 softmax 后的推论）。

## 🟡-1 KV cache 在 §5.6 推理表里出现，但 DiT 采样不需要它

**位置**：`design/…架构设计方案.md:950` → 「激活 / 工作缓冲 / **KV** — 0.6–1.2 GB」

**为什么是问题**

DiT 是扩散模型：每一步对全部 1024 个 token 做一次完整前向，**不存在跨时间步的 KV cache**（KV cache 是自回归解码的概念，每步只生成一个 token 才需要复用）。把 KV 列进 1024² 单次前向的显存表，会让人误以为存在一份需要跨 20 步保留的 K/V 张量。

补充 09 的实测也印证这一点：E5 的 20 步采样中，「激活离群比（N=512）」是**按单次前向**测的，没有累积项。

**实算参考**（KP-S，N=1024，d=1152，bf16）：K+V = 2×1024×1152×2B = 4.7 MB/layer，×24 层 = **113 MB** —— 即使真按 KV 计也只有 0.11GB，占 0.6–1.2GB 的不到 1/5。这一格的 0.6–1.2GB 主体应该是激活与 workspace。

**建议修法**：改为「激活 / 工作缓冲 / 反量化临时 — 0.6–1.2 GB」，或保留但标注「单步内 K/V 张量（约 0.11GB），非跨步 cache」。

## 🟡-5 §4.2「注意力成本几乎不变」的论证：基准口径混乱 + 「不到 2.5×」措辞不准

**位置**：`design/…架构设计方案.md:297`

**原文**：「8+32=40 通道相比 f8/c16 的 16 通道，注意力开销不变，投影开销增加不到 2.5×（且这部分在 32× 压缩后 token 数少 16×，实际绝对开销仍远低于 f8）」

**验算**

1. `40 / 16 = 2.5`，是**恰好** 2.5×，不是「不到」。措辞应为「恰为 2.5×」或「增至 2.5 倍」。
2. **「16×」缺基准**。若基准是 SDXL 的 f8 VAE（1024²/8 = 128² = 16384 token），KP 的 1024 token 确实是 16384/1024 = **16×** ✅ 算术对。但同一句里比较基准又写成「f8/c16 的 16 通道」—— SDXL 的 VAE 实际输出 **4 通道**（f8/c4），不是 16 通道。**「f8/c16」这个基准本身来源不明**。
3. **「投影开销增加 2.5×」的作用域被放大了**：latent 通道数只影响 **patch_embed**（40→d）和 **out_proj**（d→40）这两个矩阵。主干内部**所有**投影都是 d→d 或 d→3d（如 `dit.py:120` `qkv = _gl(dim, 3*dim)`），与 latent 通道数**完全无关**。所以 2.5× 只作用于 2 个矩阵，不是「投影」整体。

**建议修法**（建议直接重写这句话）
> 「注意力打分（O(N²) 项）只取决于 token 数 N，与通道数无关 ⇒ 通道数不改变注意力 FLOPs/显存。通道数只进入 **patch_embed 与 out_proj 两个矩阵**（40ch vs 16ch，恰为 2.5×）；主干内部全部投影都是 d→d 或 d→3d，不受影响。绝对开销上，32× 压缩使 token 数相对 8× VAE 少 16×（16384→1024），完全抵消这 2.5×。」

## 🟡-6 §4.2「注意力开销不变」正确，但「显存随分辨率线性而非平方增长」说得过强

**位置**：`design/…架构设计方案.md:312`

> 「**附加好处**：非 softmax 层可以只放在**低分辨率层**（前 1/3 深度），高分辨率层全线性 → **显存随分辨率线性而非平方增长**」

**代码事实**（`kp/models/dit.py:91-97`）

```python
elif kind == SIGMOID:
    scores = torch.sigmoid(q @ k.transpose(-1, -2) * scale)   # ← [B,H,N,N] 被显式物化
    out = scores @ v
```

Sigmoid 层**确实构造并持有 N×N 的 scores 张量** ⇒ 显存与 FLOPs 都是 **O(N²)**，与 softmax 层同阶。只有 `LINEAR` 分支（`dit.py:98-106`，用 `Σk⊗v` 累积）是真 O(N)。

实测 attention plan（L=24）：**1 softmax + 5 sigmoid + 18 linear ⇒ 6/24 = 25% 的层是 O(N²)**。

**为什么是问题**

「线性而非平方」这个说法过强，且它正好出现在「低显存是首要目标」的方案里 —— 读者会据此以为峰值显存随分辨率线性增长，从而低估 2K/4K 分辨率的峰值。正确表述是：N² 项的**系数降到 3/4**（而非消去），峰值注意力显存约 1/4·常数因子。

**建议改法**
> 「…高分辨率层全线性 ⇒ **O(N²) 的层数系数从 100% 降到 25%**（1 softmax 锚点 + 1/4 的 Sigmoid 层仍是平方；Sigmoid 需显式物化 N×N scores，是已知显存热点）。峰值注意力显存约为全 softmax 的 1/4，而非完全消除二次项。」
