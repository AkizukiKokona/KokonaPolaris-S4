| 分辨率 | 832×1216 占 39.3%，已按 aspect 分桶（~1MP） |

| ⇒ strict 后可用 | **≈ 12 万张**（340K × 35.2%） |

🔴 **发现一个真 bug（阻塞数据管线）**：`kp/data/rating.py::classify_rating` **在本数据集上 100% 返回 `unknown`** ——
因为该数据集**没有 `rating` / `is_explicit` / `tag_string` / `tags` 列**（它是**预筛选过的** "curated" 集），
分级信息**作为裸 token 混在 `prompt` 字符串里**：`general` / `sensitive` / `questionable` / `explicit`
（Danbooru 的 `rating:xxx` 前缀被去掉了）。
⇒ 修法：`classify_rating` 增加「**按逗号切分 `prompt`，整 token 匹配**」这一路。
⚠️ **必须整 token 匹配**，不能子串匹配（`general`/`sensitive` 是常见词，子串匹配会误判）。

📌 **parquet 读法教训**：该数据集**每片只有 1 个 row group** ⇒ `read_row_group(0)` = 读整片 1.08GB，
**"只读一个 row group" 省不了带宽**；要省必须用 **`columns=` 只选非图像列**（2.9 MB vs 1084 MB，**省 374×**）。

⭐ 理论侧结论（与 `kp/data/rating.py` 文件头一致，可引用）：**VAE 是通用编码器 ⇒ 内容无关**；
「VAE 数据加不加敏感内容」影响的是**重建保真度**（那类图压解得好不好），**不是生成倾向**（模型会不会画它）——
后者由**主干**训练数据决定 ⇒ 走「部署三层责任」(模型层/包层/部署层)。

## ⑩ 三轨道并行推进 + ⭐ VAE「内容覆盖」消融**出结论了**（commit `7c6b9aa`）

用户要求「同时解决 + 一起推进」。切成三条**互不抢资源**的轨道：

| 轨道 | 占什么 | 结果 |
|---|---|---|
| **1 网络** | 带宽 | 全量 34 片：⚠️ **两次中断**（见下），重跑后续传中 |
| **2 GPU** | 显卡 | **内容覆盖消融** ← 核心产出 |
| **3 CPU/代码** | CPU | `kp/data/predecode.py` 预解码缓存 —— ⭐ **先做它让轨道 2 快了 5 倍** |

### 轨道 3：预解码缓存（`kp/data/predecode.py`）
- AVIF 解码 **35 ms/张（纯 CPU）** ⇒ 训练 **GPU 利用率 0% / 10W**（显卡等 CPU）
- 一次解码 → uint8 memmap：**20,000 张 / 3.93GB / 8 进程 130 秒（154 张/秒）**
- 单线程仅 28.5 张/秒 ⇒ **5.4× 加速**；**训练时 GPU 0% → 61% / 71W**（瓶颈确认挪走）
- 顺带省掉 36GB 中间图片（直接从 parquet 缓存）
- ⚠️ 缓存是 **RGB（丢 alpha）** ⇒ 有 alpha 的数据集不能用

### ⭐ 轨道 2：内容覆盖消融 —— 结论（10 种子 × 3000 步 × 2 模型 = 958 秒）

设计：**等量控制变量** —— A = safe 全部(6,969)；B = **随机抽 |A| 张等量混合**(同 6,969)；
张数/步数/种子/超参全同 ⇒ **唯一差异 = 内容构成**。eval = **分层留出集**（每档 200）。

| 档位 | A_l1 | B_l1 | Δl1 | 相对改善 | 种子间 SD |
|---|---|---|---|---|---|
| safe | 0.2139 | 0.2135 | **−0.0003** | +0.15% | 0.0059 |
| sensitive | 0.2174 | 0.2147 | −0.0026 | +1.21% | 0.0069 |
| questionable | 0.2122 | 0.2076 | −0.0046 | +2.18% | 0.0065 |
| explicit | 0.2164 | 0.2097 | **−0.0067** | **+3.09%** | 0.0075 |

⭐ **三条关键读数**：
1. **单调**：改善幅度**随档位严重度单调放大**（0.15%→1.21%→2.18%→3.09%）——
   这是「真效应」的指纹，噪声不会这么排；
2. **safe 档 ≈ 零**（−0.0003）⇒ B 的优势**只落在它新增的那些档**上，
   ⇒ 机制是**内容覆盖**，**不是**「数据更杂所以泛化更好」（那会连 safe 一起变好）；
3. **显著**：非safe 平均 −0.0046，SE=0.0022，阈 0.0044 ⇒ **True**。

⇒ **结论**：**「VAE 数据里加敏感内容确实提升那类图的重建」成立，但幅度很小（~2–3%）**，
   且**完全不触及「生成倾向」**（那是主干数据决定的，本实验**没测也不能测**）。

🔴 **方法论教训（与前面那条互为镜像）**：
**先用 3 个种子跑 → 判「不显著」；加到 10 个种子 → 判「显著」。**
逐种子 Δ 在 **−0.019 ~ +0.012** 之间乱跳 ⇒ **小 n 会把真效应误判成噪声**。
⇒ 规矩：**这类小效应实验，种子数不够就不要下「无效应」的结论**。
（对照前面那条：口径不对会把假象判成结论。**两个方向都会错**。）

⇒ **下一步优先级：先投分辨率（256 → 512），容量与感知损失要各自配够预算再比。**

## ⑬ ✅ 多进程 DataLoader 落地 —— **GPU 利用率 0% → 80%**（用户选定路径）

用户拍板：「选 1（多进程 DataLoader），先做 P1」。

### 实现：`_ShardStreamSource`（`kp/train/vae_pretrain.py`）
直接从 parquet 分片**流式并行解码**：**零磁盘缓存、无分辨率上限**（缓存方案 512² 要 266GB）。

关键设计（每条都对应一个实测约束）：
- **分片外循环、分片内乱序** —— 每片只有 1 个 row group，跨片随机读会让 I/O 退化；
  一次只把一个分片的 `image` 列载入内存（~1.1GB）。
- **有界预取（prefetch）**，解码与 GPU 训练重叠。
- ⚠️ **留出评估集必须来自「单个分片」** —— `get()` 要按片载入 image 列，
  跨 34 片评估一次就要读 **37GB** ⇒ 新加 `split()` 方法，确定性选一片留出。
- `--shards` / `--workers` / `--prefetch` / `--policy`（默认 `explicit_ok` = 项目决策）。

### 🔴 踩到并修掉：**off-by-prefetch**（我自己的 bug）
生成器原本用「**已提交**」批数当终止条件；预取会**多提交 `prefetch-1` 批**
⇒ 生成器**提前 `prefetch-1` 批结束** ⇒ 消费方 `next()` 抛 `StopIteration`。
⇒ 改成按「**已产出**」计数，并在收尾 `cancel()` 掉未完成的 future。

### 机器硬事实（本轮实测）
**24 逻辑核 / 总内存 33.7GB / ⚠️ 实际可用只有 ~10GB** ⇒ 并行 worker 数不能盲目加
（每个 worker spawn 时会 import torch，~0.5GB）。

### ⭐⭐ 吞吐与瓶颈（决定性读数）
| 数据源 | 配置 | GPU 利用率 | 吞吐 |
|---|---|---|---|
| `image_dir`（原始 AVIF 单线程） | 128² b8 | **~0%** | ~29 张/秒 ← **显卡在饿死** |
| `cache`（预解码 memmap） | 128² b16 | — | **~420 张/秒** |
| `shard_stream` | 128² b16 | — | ~93 张/秒 |
| **`shard_stream`** | **256² b8** | **76–86%** | ~86 张/秒 |
| **`shard_stream`** | **512² b4** | **76–86%** | ~28 张/秒 |

⭐⭐ **结论：数据管线不再是瓶颈**（0% → 80%），256²/512² 下**已是 GPU-bound**
⇒ **继续优化 DataLoader 没有收益**，剩下的慢是显卡自己的卷积开销。

### 实用规则（记下来）
- **≤128² 快速迭代 → 用 `--cache`**（420 张/秒，快 4.5×）
- **≥256² 正式训练 → 用 `--shards`**（反正是 GPU-bound，且无分辨率上限、零磁盘）
- 已验证 **512² batch 4 可跑通**（eval 正常下降）

验收：`python -m kp.selftest` → **120/120**（`train_vae` 新增参数全为可选、向后兼容）。

## ⑭ 评估方法论定案 + 三个新坑（评估装置 `kp/train/vae_eval.py`）

### 用户问：「怎么评估？是对照实验还是需要人看？」—— 答：**自动化对照实验，不靠人眼，但必须换指标**

| 层 | 指标 | 判什么 | ⛔ 不能判 |
|---|---|---|---|
| 像素 | L1 / PSNR / **SSIM** | 保真度（像不像） | **画质（糊不糊）** |
| 结构 | Sobel-edge L1 | 轮廓在不在 | 高频细节 |
| **感知** | **LPIPS(alex)** | **感知距离（糊不糊）** | 分布级偏差 |
| **分布** | **rFID**（Inception） | 重建分布 vs 原图分布 | 单图 |

🔴 **三条方法论铁律**（都是本项目实测踩出来的）：
1. **逐像素指标测不出「糊不糊」** ⇒ 项目规范「不可判画质」是对的。
   实证：感知损失在 L1 上「更差」（0.1329 vs 0.1272）却 `edge` 几乎相同
   ⇒ **不是它没用，是指标看不见它**。
2. ⛔ **不能用训练损失本身当评估指标**（自证）。`multiscale_perceptual` 同时是
   `--w-lpips` 臂的**训练损失** ⇒ 它**不能当裁判** ⇒ 必须用**独立**的预训练度量。
3. **评估集必须固定共享**。已踩两次：旧行为 `paths[:16]` **同源**；
   各次运行随机留出集不同 ⇒ **L1 不可比**。
   ⇒ 现固化到磁盘（`out/eval/fixed2k_512.npy`，2000 张 @512²），
   且训练与评估**共用 `holdout_index()`** ⇒ 评估集 == 训练留出集，**不可能污染**。
4. **人眼只在最终验收抽查**（看有没有系统性崩坏），**不作判据**。

LPIPS **权重随包自带**（`lpips` pip 包内含 v0.0/v0.1 × alex/squeeze/vgg）⇒ 无需联网；
但它内部要 torchvision 的 AlexNet ⇒ **必须 `TORCH_HOME` 指到 D 盘**（⛔ 不落 C 盘，已设 `.torchcache`）。
实测判别力：相同图 LPIPS **0.0**、人为破坏 **0.1796** ✓。

### 🔴 坑 1：长跑只在**结束时**存盘 ⇒ 崩了全丢
120k 步长跑在 ~100k 步崩于 `MemoryError` ⇒ **56 分钟全丢**。
项目里 `kp/train/checkpoint.py` 早有 `Ckpt`（原子写 + 续跑），**但 `vae_pretrain` 没用它**。
⇒ 已接上 `--ckpt-dir` / `--ckpt-every`（默认 `max(1000, steps//20)`）/ `--resume`。
实测：20 步 → ckpt 落在 step 19(final)；`--resume` 正确从 step 20 续。

评估**一次性前向 2000 张 256²** ⇒ 申请 **7.81 GiB** ⇒ 8GB 卡直接 OOM。
⇒ `evaluate()` **分批**（64/块，逐块搬到模型 device）+ 各源 `get()` 加 `device` 参数
⇒ 评估集**直接建在 CPU**。复现验证已通过。

⚠️ 同类失误还有：**同时起了两个训练**抢同一块 GPU。
⇒ **纪律：一次只跑一个 GPU 任务；训练期间只做 IO/文档/代码级的事。**

## ⑮ ⭐ 首次「同口径 + 四层指标」对照：**20K 反超 338K**（但原因是算力预算）

### 实验（干净：两臂共用同一留出集，无污染）
两臂除「数据量」外全同：256² · batch 8 · base16 · 无感知 · 20,000 步 · seed 0
（周期存盘全程工作 ✓，26 分钟跑完两臂）。
- 臂 A：分片 0,1 ⇒ 20,000 张（训练池 **18,000**）= **8.9 个 epoch**
- 臂 B：全 34 片 ⇒ 338,011 张（训练池 **336,011**）= **0.48 个 epoch**

### 结果（2000 张固化评估集 @256²）
| 模型 | L1↓ | PSNR↑ | SSIM↑ | edge↓ | **LPIPS↓** | **rFID↓** |
|---|---|---|---|---|---|---|
| **clean_20k** | **0.1344** | **19.98** | **0.6122** | **0.3588** | **0.4353** | **217.9** |
| clean_338k | 0.1443 | 19.32 | 0.5782 | 0.3811 | 0.4941 | 244.3 |
| 随机初始化（下限参照）| 0.6601 | 8.56 | 0.0748 | 0.7052 | 1.0798 | 444.5 |

⭐ **20K 在像素 / 结构 / 感知 / 分布四层指标上全部胜出** ⇒ **不是指标口径造成的假象**。
⭐ 「随机初始化」参照让数字有了标尺：L1 0.66→0.134（**5×**）、LPIPS 1.08→0.435、rFID 444→218。

### 🔑 判读（不要误读成「数据多没用」）
固定 20,000 步预算下，小数据集走了 **8.9 个 epoch**，大数据集只走了 **0.48 个**
⇒ **当前是「步数受限」而不是「数据受限」**。
⇒ **数据量要兑现，需要更大的算力预算**（G6 租云才是它的战场）。
⇒ **本机（笔记本）迭代用 20K 子集效率最高**；338K 备好留给云端大规模预训练。

### 🔴 本轮又踩的两个坑（都已修）
1. **rFID 之前必崩**：`pytorch_fid 0.3.0` 调 `scipy.linalg.sqrtm(..., disp=False)`，
   而**本机 SciPy 已移除 `disp`** ⇒ `TypeError`。
   ⇒ 自己实现对称形式 `Tr((s2½·s1·s2½)½)`（只 `eigh` + GPU float64，秒回）。
   自检：FID(自身)=**0.0**、FID(异)=**223.4** ✓
2. **评估集加载也会 OOM**：存盘 512²，先搬 GPU 再转 float ⇒ 2000 张要 **5.86 GiB**。
   ⇒ **先在 CPU 分块缩放**（128/块）再转 float，且**默认留 CPU**、逐块上卡。
3. ⚠️ **pytorch-fid 的 Inception 权重经代理只有 ~50 kB/s**（91MB 要 **30 分钟**）
   ⇒ **必须预置权重**，否则每次评估白等半小时。

### 已在跑：338K 拉到 **60,000 步**（~1.5 小时，带周期存盘）
看它在 2.4 个 epoch 时能否追平 20K 的 0.1374 ⇒ 验证「步数受限」这个判读。
