## ② 🔴 本机环境事故：工作区内 venv 被沙箱 ACL 打死（已绕过）

**症状**：`python -m kp.selftest` 直接报
```
Cannot read 'D:\kokonapolaris-s4\.venv\pyvenv.cfg'
```
（昨天还完全正常，今天突然全体失效。）

**排查链路（一路排除，结论有点反直觉）**：
| 假设 | 实测 | 结论 |
|---|---|---|
| 沙箱令牌受限 | **关掉沙箱照样失败** | ❌ 不是沙箱运行时限制 |
| 文件损坏/编码 | `head`、基础 python 都能正常读 | ❌ 文件本身没问题 |
| 权限不足 | `icacls /grant TX:(R)` **成功**，仍失败 | ❌ 不是权限 |
| venv 损坏 | 工作区外新建/复制 venv **完全正常** | ✅ 与 venv 内容无关 |

**真因**：**工作区根 `D:\kokonapolaris-s4` 被加过硬化的 ACL**——
`Everyone:(CI)(DENY)(DC)` + `LAPTOP-...\TX:(OI)(CI)(WO)`（只有「写所有者」）
+ `S-1-4-635281079-250895385:(OI)(CI)(W,D,DC)`（疑似沙箱 AppContainer 能力 SID），
**该 ACL 向下继承** ⇒ `D:\` 之外的复制品不受影响，**工作区内的可执行文件读不了工作区内的文件**。
⚠️ 该硬化 ACL 覆盖**整个工作区根**（`.git` / `kp` / `out` 都一样），但普通读写（git / grep / head）不受影响，
**只有从工作区内启动的 python.exe 会撞上**。

**处置（已固化）**：
1. ✅ **把 venv 放到工作区外的同级目录**：`D:\kp-venv`（由原 `.venv` **整体复制**而来，零重装，
   实测 torch 2.8.0+cu128 / cuda=True / `import kp` / `portable_paths --verify`=0 全通）
2. ✅ `env.sh` 改为**优先探测 `<仓库父目录>/kp-venv`**，再回退工作区内 `.venv`；
   支持 `KP_VENV` 环境变量显式覆盖
3. ✅ 坏掉的 `.venv` **改名留档**为 `.venv.broken-20261004`（**未删除**，~4GB，待用户决定）
4. ✅ `.gitignore` 加 `/.venv*/` 与 `/kp-venv/`（锚定写法）

⭐ **通用教训**：**「工具报错文本 ≠ 根因」**（又一次）。`Cannot read 'pyvenv.cfg'` 看起来是文件/权限问题，
实际是**工作区级 ACL 硬化 + 可执行文件位置**的交互。排查时**做对照实验（工作区外 vs 内）比读文档快得多**。
